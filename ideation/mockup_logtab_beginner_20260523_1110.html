메모리 부족으로 MySQL 프로세스가 OOM Killer에 의해 강제 종료되었습니다.

서비스 영향 가능성이 있습니다. 아래 "지금 할 일"의 첫 번째 명령부터 확인하세요.

📌 결론

14:28부터 14:31까지 3분간 시스템 메모리 사용량이 95%를 넘어선 후, 커널의 OOM Killer가 메모리를 가장 많이 쓰던 mysqld (PID 4127) 프로세스를 강제 종료했습니다. 종료 직후 메모리 사용량은 38%로 떨어졌으나, 데이터베이스 연결 단절로 인한 서비스 오류 가능성이 있습니다.

🧭 원인 (추정)

  • MySQL innodb_buffer_pool_size 설정이 물리 메모리 대비 과도하게 잡혔을 가능성
  • 최근 1시간 동안 php-fpm 워커가 평소의 3배(45개)로 증가 — 동시접속 폭증 시그널
  • 스왑(swap) 미설정 또는 비활성화 상태에서 메모리 압박 발생

🚨 지금 할 일

1. MySQL이 살아있는지 확인 읽기 전용
💡 이 명령은: systemd가 관리하는 mysql 서비스의 현재 상태(실행/중지)와 최근 로그 10줄을 보여줍니다. 시스템에 아무 변경도 가하지 않습니다. 
systemctl status mysql
2. 현재 메모리 사용량 확인 읽기 전용
💡 이 명령은: 사람이 읽기 좋은 단위(MB/GB)로 메모리/스왑 사용량을 출력합니다. 안전합니다. 
free -h
3. MySQL을 다시 시작 (필요 시) ⚠ 서비스 영향
⚠ 주의: MySQL 서비스를 재시작합니다. 진행 중인 데이터베이스 연결이 끊깁니다. 1~5초 정도 서비스 중단이 발생할 수 있습니다. 위 1, 2번을 먼저 확인 후 실행하세요. 
sudo systemctl restart mysql

🗓 나중에 검토할 일

  • MySQL my.cnf의 innodb_buffer_pool_size를 물리 메모리의 50~70% 수준으로 조정
  • 스왑 파일 1~2GB 설정 (메모리 압박 시 OOM 방지)
  • php-fpm pm.max_children 값 점검 — 워커 증가 폭주 방지
  • 메모리 임계치 알람(Prometheus / CloudWatch 등) 설정
