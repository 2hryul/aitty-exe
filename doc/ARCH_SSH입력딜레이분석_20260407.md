# ARCH — SSH 터미널 키입력 딜레이 분석 및 해결방안

---

## 1. 키 입력 → 화면 표시 전체 경로

```
[사용자 키 입력]
    │  (즉시)
    ▼
xterm.js term.onData(data)
    │  (즉시)
    ▼
IPC: ssh:shell:write ──── WebView2 postMessage ──→ C# IpcHandler
    │                                                    │
    │  (~5-15ms 왕복)                                     ▼
    │                                              lock(_streamLock)
    │                                              _shellStream.Write(data)
    │                                              _shellStream.Flush()
    │                                                    │
    │                                              ── 네트워크 ──→ SSH 서버
    │                                              ←─ 에코 응답 ──
    │                                                    │
    │                                              ShellStream 버퍼에 도착
    │                                                    │
    ▼                                              ┌─────┴──────┐
[Write IPC 응답 수신]                               │  폴링 대기   │ ← ★ 병목
                                                   │ 0 ~ 500ms  │
                                                   └─────┬──────┘
                                                         │
                                                         ▼
                                              IPC: ssh:shell:read
                                              lock(_streamLock)
                                              _shellStream.DataAvailable?
                                              _shellStream.Read()
                                                         │
                                                         ▼  (~5-15ms)
                                              React: term.write(data)
                                                         │
                                                         ▼
                                              [화면에 글자 표시]
```

## 2. 구간별 지연시간 측정

| 구간 | 지연 | 유형 |
|------|------|------|
| Write IPC 왕복 | ~5-15ms | 고정 |
| 네트워크 (서버 에코) | ~2-50ms | 네트워크 |
| **폴링 대기** | **0-500ms** | **가변 — 주 병목** |
| Read IPC 왕복 | ~5-15ms | 고정 |
| Lock 경합 | ~0-5ms | 가변 |
| **합계** | **12-585ms** | |

## 3. 근본 원인: 적응형 폴링 백오프

```javascript
// SSHTerminal.tsx — 현재 설정
POLL_INTERVAL_MIN  = 50    // 데이터 있을 때
POLL_INTERVAL_MAX  = 500   // 유휴 최대치
POLL_INTERVAL_STEP = 50    // 빈 읽기마다 +50ms 증가
```

### 시나리오: 사용자가 5초간 입력 없다가 타이핑 시작

```
T+0.0s  마지막 데이터 수신 → 폴링 50ms
T+0.5s  빈 읽기 9회 → 폴링 500ms (최대치 도달)
T+5.0s  사용자 'l' 입력 → Write IPC 즉시 전송
T+5.0s  서버 에코 도착 → ShellStream 버퍼에 대기
T+5.0s  ┌──────────────────────────────────┐
        │  다음 poll 예정: T+5.5s          │ ← 최대 500ms 대기!
        │  'l' 화면 표시: T+5.5s + 15ms    │
        └──────────────────────────────────┘
T+5.5s  poll 실행 → 'l' 읽기 → 화면 표시 → 폴링 50ms로 복귀
T+5.55s 'l' 다음 입력 's' → 50ms 후 표시 (빠름)
```

**결론: 유휴 후 첫 글자가 최대 500ms 지연. 이후 글자는 50ms로 빠름.**

## 4. 부차 원인

### 4-1. Lock 경합
```csharp
// WriteToShell과 ReadFromShell이 같은 _streamLock 공유
lock (_streamLock) { _shellStream.Write(data); }  // Write 대기
lock (_streamLock) { _shellStream.Read(); }        // Read 대기
```
동시 Read/Write 시 한쪽이 블록됨. ShellStream이 thread-safe하지 않아 필수.

### 4-2. 키 입력마다 IPC 2회 왕복
1회: shellWrite (키 전송) + 1회: shellRead (에코 수신) = **최소 20-30ms 오버헤드/글자**

### 4-3. 전체 아키텍처가 Poll 기반
```
현재: React → [요청] → C# → [응답]  (매번 IPC 왕복)
이상: C# → [데이터 발생 시 즉시 Push] → React  (이벤트 기반)
```

## 5. 해결방안 (3단계)

### 방안 A — 즉시 적용 가능 (Quick Fix)

**키 입력 시 폴링 즉시 가속 + 최대 백오프 축소**

| 항목 | 현재 | 변경 |
|------|------|------|
| `POLL_INTERVAL_MAX` | 500ms | 200ms |
| 키 입력 시 | 아무것도 안 함 | 즉시 폴링 리셋 + 트리거 |

**원리:** `onData` (키 입력) 시 현재 대기 중인 poll 타이머를 취소하고 MIN 간격으로 즉시 재시작.

```
수정 전: 키 입력 → (최대 500ms 대기) → poll → 화면 표시
수정 후: 키 입력 → (즉시 poll 트리거, 15ms 후) → 화면 표시
```

**변경 파일:**
- `webapp/src/components/SSHTerminal.tsx`

**예상 효과:** 유휴 후 첫 글자 지연 500ms → 50ms, 체감 딜레이 제거

```tsx
// 폴링 가속 함수 — 키 입력 시 호출
const acceleratePolling = useCallback(() => {
  pollIntervalRef.current = POLL_INTERVAL_MIN
  if (pollTimerRef.current) {
    clearTimeout(pollTimerRef.current)
    pollTimerRef.current = setTimeout(() => pollFnRef.current?.(), POLL_INTERVAL_MIN)
  }
}, [])

// onData 핸들러에 추가
term.onData((data) => {
  shellWriteRef.current(data).catch(...)
  acceleratePollRef.current?.()  // 즉시 폴링 재개
})
```

---

### 방안 B — 중기 개선 (Push-based Read)

**C# 백그라운드 스레드가 ShellStream을 연속 읽고, 데이터 발생 시 즉시 Push**

```
현재 (Pull):  React poll 50~500ms → IPC → C# Read → IPC → React write
개선 (Push):  C# background Read (blocking) → 데이터 도착 → PostWebMessage → React write
```

**변경 파일:**
- `src/Aitty/Services/SshService.cs` — 백그라운드 읽기 스레드 추가
- `src/Aitty/Ipc/IpcHandler.cs` — Push 메시지 전송 로직
- `webapp/src/components/SSHTerminal.tsx` — Pull 폴링 제거, Push 리스너로 교체
- `webapp/src/bridge/ipcBridge.ts` — Push 메시지 수신 핸들러

**예상 효과:** IPC 왕복 1회 제거, 폴링 오버헤드 완전 제거, 지연 ~5-15ms (네트워크만)

**리스크:** 아키텍처 변경 범위 큼, 버퍼 관리/스레드 안전 주의 필요

---

### 방안 C — 장기 아키텍처 (전체 Push 전환)

Write도 fire-and-forget으로 전환, Read/Write 모두 비동기 Push 기반.
IPC 왕복 완전 제거. 가장 빠르지만 구조 변경 최대.

## 6. 권장사항

| 우선순위 | 방안 | 효과 | 난이도 | 소요 |
|---------|------|------|--------|------|
| **1 (즉시)** | **방안 A** | 500ms → 50ms | 낮음 | 30분 |
| 2 (다음 버전) | 방안 B | 50ms → 15ms | 중간 | 4시간 |
| 3 (이상적) | 방안 C | 최소 지연 | 높음 | 1-2일 |

**즉시 방안 A를 적용하여 체감 딜레이를 제거하고, 방안 B는 다음 버전에서 검토.**
